CHIP ARENA BUILDER v4 - FETCH, BUILD AND PUBLISH

UPGRADE YOUR EXISTING BUILDER
Close any running builder first. Extract this ZIP into C:\ and allow its nine
files to replace the files in C:\Chip Arena Builder. Keep Cache, Work and the
last-*.json files. The ZIP does not contain or replace any of those folders or
saved build records. You can also use a different writable folder on either PC.

EVERYDAY USE
Double-click Build-and-Publish.cmd.
It fetches the newest integrated source from codex/unity-cloud-current, builds
with Unity, validates the compiled player/update files, then publishes to the
existing test Update Game channel. No separate Publish click or typed PUBLISH
phrase is required. The native build gates must pass before upload. This runs
build/package checks, not a manual gameplay playtest.

GitHub may ask you to sign in through your browser. Use the account with access
to the source and permission to push the test channel. No credentials are bundled.

With unchanged source and local assets, a verified successful build is reused. If that source version
is already published, the command finishes successfully without another upload.
Build-and-Publish.cmd --rebuild forces a fresh local compilation when needed.

OPTIONAL LICENSED SOUNDS
Put your LocalAssets folder or LocalAssets.zip beside Build-and-Publish.cmd.
The folder wins if both exist. Before compiling, the builder runs the fetched
unity/ChipArenaConversion/tools/install_local_assets.py using its Python 3.
The installer copies sounds into the fresh project's Assets/LocalAssets/.
No input means normal fallback sounds. Adding, changing or removing the inputs
forces a new build even if the shared source is unchanged. Keep inputs stable
while building. An installer failure stops the build and publication; if the
script has not landed on the shared branch yet, wait or move the inputs away.
These licensed source files stay local: never commit or upload them to the public
repo, CI artifacts or source ZIPs. The helper ZIP includes only its nine listed
files. Only the validated compiled game goes through the existing update feed.

OTHER BUTTONS
Build-Windows.cmd         Fetch and build only, for testing before publication.
Publish-Native.cmd        Publish/retry the last successful build only.
Check-Update-Status.cmd   Compare the saved build with the public update feed.
Open-Latest-Log.cmd       Open the latest full Unity log without finding Work.

AFTER AN ERROR
The console prints the useful Unity error and recent passed checks. A short
Latest-Build-Error.txt report opens automatically in Notepad. Share that file
first. The full log is always Latest-Build.log beside these builder files;
double-click Open-Latest-Log.cmd to open it. Original logs are also kept in Work.
Each build attempt refreshes these fixed files, so an early fetch failure does
not show an older Unity error. A successful build clears the old error report.

A failed fetch or build prevents publication of an older saved build. Correct
the reported error, then rerun Build-and-Publish.cmd.
If the build passed but uploading failed, double-click Publish-Native.cmd to
retry the same compiled files without rebuilding. Old builds remain in Work.
The final output distinguishes publication on GitHub from public-feed cache
refresh. Players can use Update Game once the public feed serves the build.

ONE-TIME REQUIREMENTS
- Activated Unity 6000.3.24f1 with Windows Build Support in Unity Hub.
- Git for Windows and Python 3.8 or newer. .NET Framework 4.8 for the launcher.
- If Unity is elsewhere, set UNITY_EDITOR to the full path of Unity.exe.

FIXES RETAINED FROM v2
- Detects a real, working Git executable, including ucrt64 and mingw64 installs;
  rejects launchers that return zero without any version output.
- Uses a buffered HTTP/1.1 upload, the working solution to the observed HTTP 408.
- Publication uses an automated commit identity, so fresh laptop/desktop Git
  installs need no user.name/user.email setup. Your global Git settings stay intact.
- Uses a separate managed cache (Cache/native-publisher-v2.git). Old native-channel
  and backup folders are left alone; their staged files cannot block publication.
- Downloads the current channel trees/manifest, not its entire old binary history.
- Rechecks the remote after uploading; never force-pushes or trusts an
  "Everything up-to-date" line after an upload error.

Keep all nine builder files together. Install your playing copy outside Work.
Use one publishing PC per update. Changes must reach codex/unity-cloud-current
before the builder fetches them. Existing local Work edits are preserved, but
the combined command builds the shared source, not those local edits.
